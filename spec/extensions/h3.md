# The geo frame extension (`ext-h3`), version 0.1

**Status: proposed.** This page reserves the name and states the shape;
[`schema/extensions/ext-h3.schema.json`](../../schema/extensions/ext-h3.schema.json)
pins it, [`conformance/h3.json`](../../conformance/h3.json) with
[`conformance/outcomes/h3.json`](../../conformance/outcomes/h3.json)
checks it, and two references implement the derivation below — Rust
(`openworldformat::ext_h3`) and JS (`openworldformat/h3`). It becomes
experimental when a second implementer signs off, and leaves experimental
when a producer ships a package using it ([CONTRIBUTING](../../CONTRIBUTING.md),
[the registry](registry.json)). The RFC is
[`rfcs/ext-h3.md`](../rfcs/ext-h3.md).

The core format places entities in local metres, Y up, on a flat ground
([the world document](../world.md), "Conventions") — the right frame for
a world that is a place. A producer whose worlds live on a globe keeps a
different truth: each thing sits in a cell of the [H3](https://h3geo.org)
hexagonal grid, with an integer transform relative to that cell, so that
two clients agree bit for bit and nothing drifts. Exporting such a world
to `.world` has to flatten it to metres for the readers that know nothing
of globes, and must not lose the cell for the readers that do. This
extension carries the cell.

Everything the extension adds rides under the `ext-h3` key — on entities
(where each one is) and on the environment (where the package's local
frame sits) — so the core rule, ignore what you do not understand and
never reject a package for it, makes a globe world harmless to any
conforming reader: a reader without the extension draws the local
metres the producer wrote, and the terrace is a terrace.

## What it adds

An entity carries a **placement**: its cell, and its transform relative
to the cell's centre, in the cell's own frame, as integers.

```json
{"id": 10, "name": "column",
 "transform": {"position": [0, 0.747736, 0], "rotation_degrees": [0, 30, 0], "scale": [1, 1, 1]},
 "shape": {"Prism": {"sides": 6, "radius": 0.4, "height": 1.5}},
 "ext-h3": {"cell": "8f1fb46741a12d5", "resolution": 15, "body": "earth",
            "translation": [0, 128, 0], "rotation": [0, 3000, 0], "scale": [0, 0, 0]}}
```

The environment MAY carry a **frame**: the cell whose centre is the
origin of the package's local metres. A package whose entities carry
placements SHOULD declare one, so a reader can relate the flattened
positions to the globe; without it, a globe reader still places every
entity by its own cell.

```json
"environment": {"background_color": [0.55, 0.7, 0.9, 1.0],
  "ext-h3": {"cell": "8f1fb46741a12d5", "resolution": 15, "body": "earth"}}
```

| Field | Type | Default | Rule |
|---|---|---|---|
| `cell` | string | — | the H3 cell index, as H3's 15-digit lowercase hexadecimal string |
| `resolution` | integer 0..15 | — | the cell's resolution, stated so a reader without an H3 library knows the translation unit; MUST equal what the index encodes |
| `body` | string | `"earth"` | the body the grid is laid on, a lowercase identifier; this version defines a unit table for `earth` only |
| `translation` | `[int, int, int]` | `[0, 0, 0]` | hundredths of the mean edge length of a cell at `resolution`, along the cell frame's +X (east), +Y (up) and +Z (south) |
| `rotation` | `[int, int, int]` | `[0, 0, 0]` | hundredths of a degree, intrinsic XYZ Euler angles like the core's `rotation_degrees`; each in −18000..18000 |
| `scale` | `[int, int, int]` | `[0, 0, 0]` | log2 fixed point per axis: `round(log2(factor) × 1024)`; `0` is 1×, `1024` is 2×, `−1024` is 0.5× |

The frame carries `cell`, `resolution` and `body` with the same rules.

### The cell frame

A cell's frame has its origin at the cell's centre on the body's sphere
(`cellToLatLng`, altitude zero), +X pointing east, +Y up along the
sphere's normal, +Z south — a right-handed, Y-up frame, the core's
conventions laid on the globe. The package's local frame is the frame of
the environment's cell.

### Units

A translation unit is one hundredth of the **mean edge length** of a cell
at the placement's resolution, as H3 version 4 defines it
(`getHexagonEdgeLengthAvgM`); a reader with an H3 library asks it, one
without reads the table:

| 1 | 483056.8391 | 4830568.391 |

Rotation units are hundredths of a degree and scale units are 1/1024 of
an octave, in both directions: a producer quantises with `round` (half
away from zero), a reader dequantises by division, and the integers are
the ones the producing format stores, so an export and a re-import carry
the same bits. The quantisation is the producer's; the format only names
the unit.

For a body other than `earth`, the unit is still a hundredth of the mean
edge length at `resolution` on that body, but this version publishes no
table for it: a reader that does not know the body MUST draw the core
transform and say nothing about the globe.

## The one invariant

> **The H3 fields are authoritative. The core transform of an entity that
> carries a placement is derived from them, by the producer, as the next
> section states. A reader that understands both MUST place the entity
> by the H3 fields and MUST NOT read the core transform as a second
> truth; a reader that does not, draws the core transform.**

The invariant keeps the fold deterministic — the integers are the state,
the floats are a view of it — and keeps one entity from holding two
positions that disagree. A producer MUST write both. An authority that
knows the extension MUST keep them consistent under editing: a batch that
changes a placement re-derives the core transform; a batch that changes
only the core transform of an entity carrying a placement either removes
the placement (the entity leaves the globe frame rather than lying about
where it is) or is refused — the authority's choice, stated to the author
on the receipt. An authority that does not know the extension cannot keep
them consistent, and a reader with the extension still has the rule
above: the H3 fields win.

## Deriving the core transform

Let `R` be H3's sphere radius, 6 371 007.180918475 m, and for a point
`p = (φ, λ)` (latitude and longitude in radians) let

```
c(p)     = R · (cos φ cos λ, cos φ sin λ, sin φ)       the point on the sphere
east(p)  = (−sin λ, cos λ, 0)
up(p)    = (cos φ cos λ, cos φ sin λ, sin φ)
south(p) = (sin φ cos λ, sin φ sin λ, −cos φ)
```

be the point and its cell-frame axes in the body's Cartesian frame. For
a placement in cell `C` with translation `t = (tx, ty, tz)` in metres
(the integers times the unit at `resolution`) and the environment's
origin cell `O` (the entity's own cell when no frame is declared):

```
v        = c(C) − c(O) + tx · east(C) + ty · up(C) + tz · south(C)
position = (v · east(O), v · up(O), v · south(O))
```

```
rotation_degrees = rotation / 100           (per axis)
scale            = 2 ^ (scale / 1024)       (per axis)
```

This is exact on the sphere: the offset of the entity's cell centre from
the origin, plus the translation carried from the entity's frame into the
origin's, tilt included. When `O = C` the position is the translation.
Rotation and scale map axis by axis; the tilt between the two frames is
`d / R` radians for cells `d` apart, 0.009° at a kilometre, below the
core's rendering tolerance over the extent a package should span. A
package wider than a few kilometres SHOULD be split, since its ground
plane is a lie by then anyway.

## Conformance

The extension's conformance is the derivation, not pixels:
[`outcomes/h3.json`](../../conformance/outcomes/h3.json) pairs with
[`h3.json`](../../conformance/h3.json), a terrace of four placed entities
in three cells. The fixture carries `cellToLatLng` of every cell it names
as data — no reference embeds an H3 library — and a runner with one
SHOULD verify them. The assertion kinds:

| Assertion | Checks |
|---|---|
| `frame` | the environment declares exactly this cell, resolution and body |
| `edge_length` | the unit table says `metres` at `resolution`, within `tolerance` |
| `placed` | the entity's derived transform and its core transform are both within `tolerance` of `position`, `rotation_degrees` and `scale` — the invariant checked from both ends |

A renderer without the extension draws the world flat (its conformance,
through the core render check); a reader claiming the extension passes
the outcomes.

## Reference implementations

Two, running the same outcome assertions in CI, with the same code line
for line:

- **Rust** — `openworldformat::ext_h3`: the unit table and quantisation
  (`quantize_translation`, `quantize_rotation`, `quantize_scale` and their
  inverses), the block readers (`frame_of`, `placement_of`), the
  derivation (`local_position`, `derive_transform`) and `run_outcomes`.
- **JS** — `openworldformat/h3`: the same surface in camel case.

Python, Swift and Kotlin carry the blocks through the fold untouched
(every `ext-*` key rides along) and admit the name in strict mode.
